## Result

This is evidence for the tested configuration, not a guarantee for every combination of pipeline variants or driver version.

## Separate source finding: reserve arguments use capacity instead of length

While reading the warning sites, a separate allocation-contract bug was found at `crates/render-core/src/lib.rs:802-804`: after clear(), `try_reserve_exact(output_size - capacity)` does not guarantee capacity for output_size elements. Reserve arguments are additional to **length**, not capacity ([official Vec contract](https://doc.rust-lang.org/std/vec/struct.Vec.html#method.try_reserve_exact)). For example, len 0 / cap 8 / target 12 asks for 4 additional elements, so reserve can do nothing; later pushing past 8 can allocate outside the intended fallible reservation. This is a source-contract finding, not a measured OOM or this startup cause.

Sibling search found the same pattern at `src/app/image_sequence.rs:627,665,692`, `crates/render-3d/src/pt/blit.rs:291,296,316`, and `crates/render-3d/src/env_map.rs:178`. Each was checked around clear()/reserve()/push. The environment mip loop normally starts with the largest mip and reuses its capacity while sizes shrink, so the problematic growth branch is not normally reached there after the first empty allocation.

Proposed repair: reserve the required additional amount relative to current len (the full target after clear), preserving Result-based allocation failure where currently promised. Verify a reused buffer whose next target lies between old capacity and twice that capacity. No source repair was made. The relevant API review principle is [meaningful error handling](https://rust-lang.github.io/api-guidelines/checklist.html), not warning suppression.
